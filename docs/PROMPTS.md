```
Astra 1회차  분석·계획      → docs/PLAN.md, docs/TASKS.md, docs/RUN-P0.md ~ RUN-P8.md 생성 (코드 없음)
Astra 2회차  Phase 0 실행   → RUN-P0.md 를 자기가 실행

## 1. Astra — 1회차: 분석·계획 (코드 작성 금지)

> **이 턴에서만 스펙 전체(약 43k 토큰)를 읽는다.** 그 대가로 이후 모든 턴이 읽을 양을 줄이는 산출물을 만든다.

```
너는 바름닷컴 프로젝트의 기술 리드다. 이번 턴에서는 코드를 한 줄도 쓰지 마라.
분석하고 계획만 세운다.

[읽을 것 — 이번 턴은 전부 읽어라]
AGENTS.md 와 docs/ 아래 00-INDEX.md 부터 17-appendix.md 까지 전부.
이번 턴은 전체 맥락을 잡는 것이 목적이므로 예외적으로 전부 읽는다.
단 bareum_com_implementation_brief.md 는 구버전이므로 읽지 마라.

[배경]
이 스펙은 한국 커뮤니티 조사를 기반으로 작성됐고, 경쟁사(Windy, 바다타임, 기상청)의
확인된 약점 14개(G1~G14)를 기능으로 연결해 놓은 상태다.
디자인은 시안 4장에서 토큰과 컴포넌트로 번역되어 있다.
구현은 다른 모델(GPT-5.6 Sol)이 이어받는다. 너는 그 모델이 실수하지 않게 만드는 역할이다.

[산출물 1 — docs/PLAN.md]
스펙을 비판적으로 읽고 아래를 작성해라. 스펙을 요약하지 마라. 이미 있는 내용을 옮겨적는 건 무가치하다.
1. 모순·충돌: 서로 어긋나는 명세 (예: 어떤 문서는 A라 하고 다른 문서는 B라 하는 곳)
2. 누락: 구현하려면 반드시 필요한데 스펙에 정의가 없는 것
   (예: 검색 인덱싱 방식, spots 초기 데이터 확보 경로, 지도 타일 제공자 확정,
    오프라인 캐시 무효화 규칙, 에러 재시도 정책의 구체값)
3. 구현 불가·과도: 현재 기술·비용으로 무리이거나, 투입 대비 효과가 낮은 항목 → 축소안 제시
4. 순서 오류: 로드맵의 Phase 순서상 앞 단계에서 결정해야 하는데 뒤로 밀린 것
5. 숨은 의존성: 스펙에 명시 안 됐지만 실제로는 A가 끝나야 B가 되는 관계
각 항목마다 [영향도 상/중/하] 와 [권고안] 을 붙여라.

[산출물 2 — docs/DECISIONS.md]
구현 전에 확정해야 하는 기술 결정 목록. 각 항목에:
- 결정이 필요한 이유 / 선택지 2~3개 / 장단점 / 너의 권고안 / 되돌리기 비용(상·중·하)
AGENTS.md 의 "확인 필요" 분류에 해당하는 것은 권고안만 쓰고 결정하지 마라. 사람이 결정한다.
그 외는 네가 결정하고 그 근거를 남겨라.

[산출물 3 — docs/TASKS.md]
Phase 0~8 을 실행 가능한 작업 단위로 분해해라. 각 task 에:
- ID (P0-01 형식) / 제목 / 담당 모델(Astra|Sol) / 선행 task / 산출 파일 경로
- 완료 조건 (검증 가능한 문장. "잘 동작한다" 같은 건 금지)
- 참조할 docs 파일과 절 번호
task 는 한 번에 끝낼 수 있는 크기로 쪼개라. 너무 크면 Sol 이 중간에 길을 잃는다.
마지막에 의존성 그래프와 병렬 가능 구간을 표로 정리해라.

[산출물 4 — docs/RUN-P0.md ~ RUN-P8.md]
각 Phase 마다, 그 Phase 담당 모델에게 그대로 붙여넣을 실행 명령문을 작성해라. 각 파일에:
- 읽어야 할 docs 파일 목록 (그 Phase 에 실제로 필요한 것만. 전체를 읽게 하지 마라)
- 해당 Phase 의 task 목록 (TASKS.md 에서 가져옴)
- 반드시 지킬 규칙 (AGENTS.md R1~R12 중 그 Phase 에서 특히 위험한 것만 골라서)
- 그 Phase 에서 흔히 저지를 실수와 올바른 방법
- 완료 조건 = docs/15-roadmap.md 의 해당 Phase DoD
- 다음 담당자에게 남길 인수인계 파일(HANDOFF) 작성 지시
docs/00-INDEX.md 의 "Phase → 읽을 파일" 표를 기준으로 삼되, 네가 분석한 결과
읽을 파일을 더하거나 뺄 필요가 있으면 조정하고 그 이유를 적어라.

[산출물 5 — docs/RISKS.md]
이 프로젝트에서 실제로 터질 지점. 각 항목에 징후·예방·터졌을 때 대응.
최소한 다음은 다뤄라: 외부 API 쿼터/장애, 지도 레이어 성능, CCTV 재배포 권한,
GPL 라이선스, Firebase 비용 폭증, 다국어 번역 품질, 안전 기능의 법적 책임.

[작업 방식]
- 코드를 쓰지 마라. 파일 생성은 위 5개 마크다운 문서뿐이다.
- 각 문서는 간결하게. 스펙 내용을 복사해 붙이지 말고 참조(파일명 + 절 번호)로 가리켜라.
  중복은 유지보수 비용이고 토큰 비용이다.
- 다 끝나면 마지막에: 가장 위험한 항목 3개와 사람이 지금 결정해야 할 것 3개를 요약해라.
```

## 2. Astra — 2회차: Phase 0 실행

> 1회차가 만든 `RUN-P0.md` 를 Astra 자신이 실행한다.

```
docs/PLAN.md 와 docs/DECISIONS.md 에서 네가 정리한 결론을 전제로, 이제 Phase 0 을 구현한다.

docs/RUN-P0.md 를 읽고 그대로 실행해라.
RUN-P0.md 가 지정한 파일 외에는 읽지 마라.

사람이 결정해야 한다고 표시한 항목(DECISIONS.md)이 아직 미결이면,
그것 없이 진행 가능한 부분까지만 하고 무엇이 막혔는지 명시해라.

완료 후 docs/15-roadmap.md 의 Phase 0 DoD 체크리스트를 통과/미통과와 함께 출력하고,
docs/HANDOFF-P1.md 를 작성해라.
```

## 3. Sol — Phase 실행 템플릿

```
너는 바름닷컴 프로젝트의 Phase [N] 을 구현한다.

[읽을 것]
1. AGENTS.md
2. docs/RUN-P[N].md  ← 이 파일이 이번 작업의 지시서다. 여기 적힌 대로 한다.
3. docs/HANDOFF-P[N].md  ← 이전 담당자 인수인계
RUN-P[N].md 가 지정한 docs 파일만 읽어라. 그 외는 읽지 마라. 토큰 낭비다.
bareum_com_implementation_brief.md 는 읽지 마라.

[규칙]
AGENTS.md 의 R1~R12 를 전부 지킨다.
스펙에 명시된 값(색상, 크기, 임계값, 캐시 TTL, API 계약)을 임의로 바꾸지 마라.
바꿔야 한다고 판단되면 멈추고 이유와 함께 질문해라.
docs/DECISIONS.md 에서 이미 결정된 사항은 재논의하지 마라.

[완료 조건]
docs/15-roadmap.md 의 Phase [N] DoD 를 항목별 통과/미통과와 함께 출력.
전부 통과 전에는 다음 Phase 로 넘어가지 마라.
완료 후 docs/HANDOFF-P[N+1].md 작성.
```

**담당**: Phase 1·2·3·4·6·7·8 → Sol / Phase 0·5 → Astra

```

[읽을 것]
AGENTS.md / docs/RUN-P[N].md / docs/15-roadmap.md 의 Phase [N] DoD / 변경된 코드(git diff)

[검수 항목]
1. DoD 각 항목이 실제로 충족되었는지 — 주장이 아니라 코드로 확인
2. R1~R12 위반, 특히:
   하드코딩된 색상값·한국어 문자열 / 지점·격자 데이터 혼용 /
   외부 API 타입이 UI 로 새어나간 곳 / NEXT_PUBLIC_ 에 들어간 비밀키 /
   다크·라이트 한쪽만 확인된 컴포넌트
3. 스펙 명시값(색상, 임계값, 캐시 TTL, API 계약)과 코드의 일치 여부
4. 되돌리기 어려운 결정이 조용히 내려진 곳 (스키마, 보안 규칙, 외부 의존성)
5. docs/DECISIONS.md 에 없는 새 결정이 임의로 내려졌는지

[출력]
통과 / 조건부 통과 / 반려 판정 + 파일:줄 단위 수정 지시 + 다음 Phase 진행 가부
